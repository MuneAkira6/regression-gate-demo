# 素材：著者の回帰テストと品質ゲートの実践（このリポジトリを書くための一次資料）

> ワーカーへ：著者の実務について書いてよいことは、このファイルがすべてです。ここにないことを実務の話として書かないでください。書き方は自分の言葉で。実務の数字は一つも書きません（README の「結果」は事例へのリンクで示します）。会社・製品・チーム・人の名前は出てきませんし、書いてもいけません。サンプルアプリは架空の「Acme Tasks」です。

## 1. 状況

- Web ポータルの回帰テストは手動が中心で、機能仕様書はあっても「どこまでテストされているか」を誰も数えていませんでした。
- 共有のステージング環境を複数のチームが使い、一日に何度も再デプロイされます。テストの実行中に、被テスト版が入れ替わることがあります。

## 2. 分母を先に作る

- 仕様の側から「画面 × シナリオ × 変種」を 1 行とする目録を作り、それを分母にしました。書いたテストの数ではなく、目録に対して何行を覆っているかを数えます。
- 数えるのはスクリプトで、手では数えません。
- 「別の場所で覆われている」として分母から外した行も、あとで疑います。参照先は存在するか、実際に実行されているか、変種の軸が抜けていないか。成り立たないものは分母に戻します。数字は下がっても、正直な分母を選びます。

## 3. 手動テストとの対応

- 手動の回帰テストシートの用例 ID、シートの行、自動テスト（spec）のタイトルを、同じ ID で一対一に対応させます。
- 自動化しないもの（人の目で見る項目など）と対象外のものは、理由をつけてシート上で区別します。

## 4. 失敗を分類してからゲートにする

赤いテストを、次の四つに分けます。

| 分類 | 条件 | 扱い |
|---|---|---|
| NEW RED | 申告されておらず、被テスト版も変わっていない | 失敗。同じビルドで再現を確かめる |
| KNOWN RED（申告済みの赤） | 理由と出典つきで申告されている | 失敗に数えないが、一覧には必ず出す |
| INCONCLUSIVE | その単位の実行の前後で、被テスト版が変わった | 失敗に数え、同じビルドでの再実行を案内する |
| WENT GREEN | 申告済みの赤が緑になった | 報告だけ。申告（ベースライン）は自動では書き換えない |

- 申告できるのは「赤でも製品が壊れているわけではない」ものだけです。たとえば、環境に外部の仕組みがなくて試せないもの。製品の欠陥を申告で隠してはいけません。
- 版をまたいで緑になったものは、修正された証拠として扱いません。
- 単位（spec ファイル）ごとに 1 プロセスずつ直列に流し、各単位の前後で被テスト版を読み取ります。

## 5. 不安定さへの対策

- 不安定さの多くは、待ち方にありました。ローディング表示が消えたかどうかといった「状態」を待つと、描画途中の値を読んでしまいます。
- 読み取った値が N 回続けて一致するまで待ちます。N はコントロールごとに決めます（実務では 2〜5 回）。
- retries は 0 にします。再試行で赤を隠さないためです。
- ネットワークの監視は、クリックより先に仕掛けます。
- 仕上げの段階では、同じファイルを 2 回続けて流し、ケースごとに結果が一致するかを確かめます。

## 6. 判定基準を凍結する

- 期待値は、仕様と UI の文言表からだけ取ります。ソースコードは観察を説明するためだけに読み、期待値を下げる根拠にはしません。
- 製品の判定ロジックをそのまま写したテストは、ときどき赤くなっても緩めません。緩めると、ユーザーに影響している欠陥を、測る側から消してしまうからです。

## 7. 測る側を疑う

- CI でだけ赤くなるケースがありました。同じビルド・同じマシンで、変える変数を一つだけにして比べ、原因がテスト側の監視の競合だと確定しました。製品の欠陥ではありませんでした。
- ゲート自体にも、負の自己テストを付けました。実際に再デプロイをまたいだ実行を流すと INCONCLUSIVE になり、同じビルドの実行では NEW RED のまま残ることを確かめています。

## 8. 運用

- CI のワークフローは回帰ゲートとして手動で起動していました。マージのたびに走るゲートにはしていません。
