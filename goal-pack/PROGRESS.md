| 2026-09-30 | 「動かし方」's `&&` chain no longer contains `pnpm e2e`, and CI's `e2e` step does not fail the job (reason recorded **before** the change, as SCOPE.md requires) | SCOPE.md gives the documented line as `pnpm i && pnpm exec playwright install chromium && pnpm test && pnpm e2e && pnpm gate`. On a healthy repository `pnpm e2e` exits 1, because TB-011 is a declared red and the raw suite has no notion of a declaration — only the gate has. So `&&` stops the chain at `pnpm e2e` and never reaches `pnpm gate`, which is the one command that can tell a declared red from a new one. The chain as written can therefore never succeed, and in CI a step that always fails would leave a healthy repository showing red for ever. <br>**The three things I would not do.** Weaken TB-011 — that would delete the only signal the test-email feature does not work. Give `pnpm e2e` a passing exit code — a red is a red, and a suite that reports 0 while a test fails is the measuring side lying. Drop `pnpm e2e` quietly — a reader must be able to run the raw suite. <br>**What I did instead.** The documented chain is `pnpm i && pnpm exec playwright install chromium && pnpm test && pnpm gate`, and `pnpm e2e` is documented on its own line immediately beside it, with its expected `exit 1` and the reason. Nothing goes unexecuted: `pnpm gate` runs exactly the same six spec files and the same 21 tests as `pnpm e2e` (its per-unit counts are 1 + 9 + 1 + 2 + 1 + 1 + 6 = 21), one file per unit. What changes is only which command's exit code is the verdict, and the README says so in as many words — the gate is the authority, `pnpm e2e` is the raw view. <br>In `.github/workflows/ci.yml` the `e2e` step is kept and still runs, with `continue-on-error: true` and the reason in a comment in the workflow file itself, because the next person to open that file will be opening it because CI went red. The `gate` step decides the job. <br>Marked as a difference in the AS-BUILT contract. |
| 2026-09-30 | the coverage report's `automated` column is a **measurement**, not the sheet's plan (decision recorded at the bus's request) | SCOPE.md says only "per domain × priority: cases, automated, manual, n/a, and coverage = automated ÷ (cases − n/a)", which does not say whether `automated` counts the cases *marked* `ui`/`api` or the cases a test actually claims. `materials/practice.md` §2 settles it: 「仕様の側から…目録を作り、それを分母にしました。書いたテストの数ではなく、目録に対して何行を覆っているかを数えます」 — the figure counts how many rows of the sheet are *covered*. §2 also says an exclusion is to be re-examined rather than trusted, which only means something if the number can move. Under the plan reading the percentage is a restatement of the CSV and can never fall, so the report could not do the one job it exists for; and a bucket printing `100.0%` beside its own gap in the same output is indefensible under either reading. So `automated` counts a case when the sheet says it should be automated **and** a test claims its id. `manual`, `n/a`, the denominator, the gap list, the orphan list and the exit codes are unchanged, the printed output for the real sheet is byte-identical, and the column keeps the contract's name. |
| 2026-09-30 | `playwright.config.ts` made conditional on `GATE_SPECS` (frozen in G0, changed here with reason) | `testIgnore: ["**/fixtures/**"]` is what the contract asks for, and it must stay for `pnpm e2e`. With `GATE_SPECS` unset the configuration is byte-for-byte equivalent to the frozen one — `playwright test --list` still reports `Total: 21 tests in 6 files` with `0` fixture lines. `playwright.config.ts` is a deliverable, not a given file, so no red line is crossed. |
| 2026-09-30 | the gate reads each unit's JSON report from a file named by `PLAYWRIGHT_JSON_OUTPUT_NAME`, not from stdout | The contract's unit command is `playwright test <file> --reporter=json --retries=0 --workers=1`. Parsing that stdout would be unsafe, because the same stream carries other output — with the output file set, stdout began `[WebServer] $ node apps/sample-app/server.ts` followed by `Running 1 test using 1 worker`.
